# PinCon 알림 빈도 진로 탐구 · career-v3

운영 주소: https://pincon.app/experiments/

## 바로 시작하기

1. 대상 학급 관리자(회장·교사)의 학번/PIN 또는 학교 관리자 Google 계정으로 로그인한다. 기존 PinCon 로그인도 공유한다. 상단에서 현재 계정·권한을 확인하고 계정을 변경하거나 권한을 다시 확인할 수 있다.
2. **설계**에서 학급, 시작일, 기준선과 조건별 기간, 평일 여부와 제외일을 확인한다. 기본값은 현재 선택 학급, 기준선 2일 + 조건별 4일이다.
3. **설계 저장 · 균형 배정**을 누른다. 활성 계정 전체를 선택 학급 범위에서 사전배정한다. 이미 확보한 동의를 전제로 하며 재동의를 요구하지 않는다.
4. **설계 → 실험 시작**을 누른다. 최근 정상 서버 점검이 필요하다. 이전 UI 실험이 실행 중이면 학교 관리자가 먼저 일시정지한다.
5. **배정**에서 참가자별 조건과 기기 등록을, **발송·반응**에서 서버 점검과 실제 기록을 확인한다.
6. **결과**에서 익명 CSV/JSON을, **보고서**에서 3차시 탐구 메모·실제 집계 결과를 내려받는다.

설계 저장만으로는 발송되지 않는다. 설계와 이전 버전 보관을 먼저 저장하고, 서버 규칙의 연산 한도를 지키도록 계정별 배정을 저장한 뒤 전체 완료 표시를 기록한다. 중간에 실패한 미완료 설계는 화면과 서버 규칙 모두 시작을 막으며, 다시 저장해 새 버전을 준비할 수 있다. 시작하면 기준선부터 행동을 수집하며 기준선에는 실험 푸시를 발송하지 않는다. 기준선 0일로 08시 이후 시작하면 당일을 제외한다. 온전한 3회 노출이 불가능한 날을 정식 비교에 포함하지 않기 위함이다.

## 연구 질문과 설계

주제: 알림은 많을수록 효과적인가? 모바일 서비스의 알림 빈도가 사용자의 이용 행동에 미치는 영향.

- LOW 0회 / MID 1회 / HIGH 3회. 중요 공지·안전 알림은 모든 조건에 동일하게 제공하고 실험 예산에서 제외한다.
- 같은 참가자가 세 조건을 경험하는 여섯 순서를 균형 배정한다. 무작위 seed와 결과를 보관하고 시작 후 재배정하지 않는다.
- 학교 수업을 피하는 KST 08시·17시·19시만 사용한다. MID는 참가자·날짜별로 세 시간대를 회전하며 HIGH는 세 시간대를 모두 사용한다.
- 비필수 수행평가·준비물과 중립적인 확인 문구를 사용한다. 모든 조건에서 같은 정보를 직접 열 수 있다.
- 평일·제외일 설정을 서버와 브라우저가 같은 모듈로 계산한다. 기준선에서는 기존 일상 요약 알림도 억제하고 중요 알림만 유지한다.
- 예비 실험은 `studyKind=pilot`인 별도 버전으로 저장한다. 예전 브라우저 로컬 pilot은 합산하지 않으며 `/research/`는 통합 화면으로 이동한다.

## 수집과 해석

주요 지표는 참가자별 **정보 확인일 / 경과 실험일**의 평균이다. 미접속 계정도 0일로 포함하며 미래 기간은 분모에 넣지 않는다. 오늘은 진행 중인 관측일이다.

보조 지표는 이용일 비율, 알림 ID별 클릭·수신·5/30/60분 클릭 진입률, 실제 상세 열람, 기간별 유용성·피로도·이용 증가·지속 희망과 적정 횟수 설문이다.

- FCM 수락, SW 수신 기록, 클릭, 상세 열람은 서로 다르다.
- 연결 화면이 열렸다는 이유만으로 정보 확인을 기록하지 않는다. 사용자가 실제 상세를 열 때 계측한다.
- 0회 조건의 클릭률은 분모가 없으므로 빈 값으로 출력한다.
- 동일 알림 ID의 중복 이벤트를 제거하고 실패 발송을 클릭률 분모에 넣지 않는다.
- 새 버전 결과는 해당 `experimentVersion`만 집계한다. 설문 문서도 `v{version}-period-{period}`로 분리한다.
- 기간 마지막 날 20시부터 설문을 제공한다. 필수 학급 화면을 강제 응답 대화상자로 가리지 않는다. 설문을 선택하면 네 문항과 선호 횟수를 모두 답해야 제출된다.
- 한 학급의 반복 관측이다. 기간·요일 효과, 기기 미등록, 미응답과 수신 계측 누락을 함께 보고하고 자동으로 최적 빈도나 통계적 유의성을 선언하지 않는다.

## 운영과 보관

`notification-frequency.yml`은 약 10분마다, 관련 코드의 main 반영 직후, 수동 실행 시 독립적으로 동작한다. Actions 시간은 지연될 수 있으므로 정확한 정각 도착을 보장하지 않는다. 시각별 00~55분에만 처리하며 TTL은 1시간이다.

- 대표 기기 1대, 계정 전체 수신 중지, 만료 토큰 정리와 최대 3회 재시도를 유지한다.
- v3 발송 선점 키는 참가자·버전·날짜·기간·슬롯이다. 같은 슬롯의 콘텐츠가 바뀌어도 추가 발송하지 않는다.
- 선점 트랜잭션에서 ACTIVE·버전·flag·계정 수신 설정을 다시 확인한다.
- 수락 뒤 기록 실패는 `send-uncertain`으로 남기고 자동 재발송하지 않는다.
- 배포 시 실행 중인 구형 알림 실험은 설정과 배정을 보관한 뒤 일시정지한다. 새 설계는 관리자 화면에서 시작한다. 기존 원자료는 삭제하지 않는다.
- 일시정지·재개 시 중단에 걸친 날짜를 제외하여 조건별 관측일을 확보한다. 중도 종료 후에는 후속 날짜를 분모에 넣지 않는다.
- 버전별 설정·배정은 `runs`에, 직접 작성한 메모는 `researchNotes/v{version}`에 보관한다.

새 진로 연구는 UI 실험의 과거 `COMPLETED/next` 승격을 요구하지 않는다. 동시 UI 실험은 계속 차단한다. v1/v2 호환 경로의 기존 분리 조건은 유지한다.

## 권한과 익명 자료

계정 명단은 기존 인증된 account API에서만 가져온다. 계정 DB를 브라우저에 추가 공개하지 않는다. 참가자는 자신의 배정·설문·알림 설정만 조회한다. 학교 관리자는 전체 연구를 운영한다. 학급 관리자는 현재 연구의 모든 대상 학급이 자신의 서버 권한에 포함될 때만 운영하며, 현재 버전의 알림 연구 기록·담당 학급의 기기 상태·연구 메모만 읽는다. UI 실험·다른 학급 기기·이전 버전 원자료·역할 변경은 허용하지 않는다. 전체 보관 이력은 학교 관리자만 읽는다.

서버는 토큰을 포함하지 않는 `notificationStudyDevices/{uid}`와 `experimentRuntime/notification-frequency`를 기록한다. 브라우저에서 이 문서들을 조작할 수 없다. 익명 CSV/JSON에는 UID, 이름, 학번, 토큰, 관리자 ID를 포함하지 않는다.

## 검증

- 기본·회귀·연구 분석 테스트와 메모리 DB 기반 실제 dispatcher 테스트
- Firestore Emulator에서 실제 관리자 서비스의 34명 배정 → 시작 → 조회 → 메모 저장 → 일시정지와 접근 제한 검증
- 외부 FCM/OS 실제 수신은 기기 권한과 운영 환경에 의존한다. 기기 표시 테스트는 로컬 알림 표시만 검증한다.
